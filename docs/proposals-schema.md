# Proposals schema

Application tables for the Proposals family (Quotation, Project Proposal, Retainer Proposal, Change Request) and the studio details printed on every document. All are defined in `src/server/db/schema.ts` and were **applied to the Neon production branch on 13 Nov 2026**.

Neon Auth still owns identity (see `auth-schema.md`). Every `*_by` column stores the opaque Neon user ID from the verified server session, with no foreign key into `neon_auth`, for the same reason as `audit_events`.

## `proposals`

One row per offer version. All four document types share the table: the columns hold what the list and lookups need, and `content` holds the rest of the document.

| Column               | Type             | Purpose                                                                                                                      |
| -------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| id                   | uuid             | Primary key, generated by the app on create                                                                                  |
| type                 | text             | `quotation`, `project`, `retainer` or `change`                                                                               |
| sequence             | integer          | Number within the type: the `001` in `BW-Q-001`                                                                              |
| version              | integer          | 1 for the original, 2+ for revisions (`BW-Q-001 v2`). Default 1                                                              |
| status               | text             | `draft`, `sent`, `accepted` or `replaced`. Default `draft`                                                                   |
| title                | text             | First line of the description; derived from `content` on every save. Default `''`                                            |
| client_name          | text             | Business name, else client name; derived on every save. Default `''`                                                         |
| issue_date           | date, nullable   | Document date (IST calendar day); derived on every save                                                                      |
| total_paise          | bigint, nullable | Total in paise (₹1 = 100); derived on every save; null when there are no line items                                          |
| replaces_id          | uuid, nullable   | For a revision: the version it replaced                                                                                      |
| original_proposal_id | uuid, nullable   | For a Change Request: the accepted Project Proposal it changes (used from the Change Request phase)                          |
| content              | jsonb            | The document's fields, validated with the type's zod schema (`src/features/proposals/templates/*`) on every write            |
| row_version          | integer          | Starts at 1 and goes up on every write. Autosave must send the version it edited, so a stale tab cannot overwrite newer work |
| created_by           | text             | Neon user ID of the creator                                                                                                  |
| updated_by           | text             | Neon user ID of the last writer                                                                                              |
| created_at           | timestamptz      | Server-generated                                                                                                             |
| updated_at           | timestamptz      | Server-generated, set on every write                                                                                         |

**Constraints**

- `type` and `status` must be one of the values above (CHECK). These mirror `PROPOSAL_TYPES` and `PROPOSAL_STATUSES` in `domain.ts`, the single source of truth.
- `sequence > 0`, `version > 0`, and `total_paise` is null or ≥ 0.
- `content` must be a JSON object.
- `(type, sequence, version)` is unique, so two offers can never get the same number.
- `replaces_id` and `original_proposal_id` reference `proposals.id` with `ON DELETE RESTRICT`: an offer that is referenced cannot be deleted.

**Indexes**

- `(status, type)`: list filters and the accepted-projects lookup.
- `issue_date`: the list's default sort.

## `proposal_counters`

| Column     | Type    | Purpose                                            |
| ---------- | ------- | -------------------------------------------------- |
| type       | text    | Primary key; same CHECK as `proposals.type`        |
| last_value | integer | Last sequence number used for that type. Default 0 |

There's no seed data. The first create of a type inserts its row. Every create increments the counter and inserts the draft in a single statement, so concurrent creates never get the same number. A deleted draft leaves a gap in the numbers. That's accepted; numbers are never reused.

## `studio_settings`

| Column     | Type           | Purpose                                                                                                                                                |
| ---------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| id         | smallint       | Primary key; CHECK `id = 1`, so there can only ever be one row                                                                                         |
| content    | jsonb          | Address, phone, email, website, UPI ID, bank account (name, number, IFSC, bank), signatory name and role; validated by `src/features/studio/schema.ts` |
| updated_by | text, nullable | Neon user ID of the last editor                                                                                                                        |
| updated_at | timestamptz    | Server-generated                                                                                                                                       |

The bank details are the same ones printed on every PDF for clients, so they aren't secrets. They are still only readable and writable by signed-in users, through server code.

## `audit_events`

Unchanged from `auth-schema.md`, and applied in the same run. Audit persistence is now implemented in `src/features/audit/service.ts`. Each event is written **in the same SQL statement** as the change it records, so an event exists only if the change committed. Recorded events:

| action                    | entity_type                        | metadata       |
| ------------------------- | ---------------------------------- | -------------- |
| `proposal.created`        | `proposal`                         | `{ type }`     |
| `proposal.status_changed` | `proposal`                         | `{ to }`       |
| `proposal.revised`        | `proposal` (the new version)       | `{ replaces }` |
| `studio_settings.updated` | `studio_settings` (entity_id null) | `{}`           |

Autosaves aren't audited, because they're too frequent to be useful. `updated_by` and `updated_at` on the row record the last writer instead.

## Write paths

The app connects with `drizzle-orm/neon-http`, which has no interactive transactions. Every write that has to be atomic is a single SQL statement.

| Use case       | What happens                                                                                                                                                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Create         | Increment the counter, insert the draft and insert the audit event, in one statement                                                                                                                                                                   |
| Autosave       | `UPDATE … WHERE id AND row_version = expected AND status = 'draft'`. No row matched → "changed elsewhere" (or read-only if no longer a draft)                                                                                                          |
| Status change  | Allowed: draft → sent → accepted, and sent → draft. Update the row and insert the audit event in one statement, guarded on the current status                                                                                                          |
| Revise         | Only for sent/accepted offers. Insert `version + 1` as a draft, mark the old one `replaced` and insert the audit event, in one statement guarded on the old row's status and `row_version`. A repeated revise hits the unique number and fails cleanly |
| Studio details | Upsert the single row and insert the audit event, in one statement                                                                                                                                                                                     |

Every server action checks the session and validates its input with zod before calling the database.

## How it was applied

1. Migration files: `drizzle/0000_audit_events.sql`, then `drizzle/0001_proposals.sql`. They only create things: 4 tables, 2 foreign keys, 1 unique constraint and 5 indexes (3 on `audit_events`, 2 on `proposals`). Nothing existing was altered or dropped, and `neon_auth` is untouched.
2. They were applied on 13 Nov 2026 to the Neon **production** branch with Drizzle's migrator (`drizzle-orm/neon-http/migrator`), using `DATABASE_URL` from `.env`. They're recorded in `drizzle.__drizzle_migrations` (rows 2 and 3), so they won't run twice. `drizzle.config.ts` stays credential-free.
3. A read-only check afterwards confirmed all four tables, their constraints and indexes, and both migration records.

**Found during the check:** `public` already had seven tables from an earlier local-auth migration that was applied at some point (row 1 in `drizzle.__drizzle_migrations`): `user`, `account`, `session`, `verification`, `allowed_email`, `audit_event` (singular) and `rate_limit`. They're unused by the app and nearly empty (one row each in `verification` and `rate_limit`). They were left as they are; dropping them needs a separate decision.

**Rollback**, only if needed before real data exists:

```sql
DROP TABLE proposals, proposal_counters, studio_settings, audit_events;
DROP TABLE drizzle.__drizzle_migrations;
```
