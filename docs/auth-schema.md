# Authentication and audit schema

Authentication uses Neon managed Better Auth. Neon owns users, password credentials, sessions, and verification records in its `neon_auth` schema. Do not create or migrate duplicate identity tables with Drizzle.

The app uses `@neon/auth` through `src/server/auth.ts` and the same-origin `/api/auth/[...path]` handler. Browser input schemas in `features/auth/schema.ts` validate form values; these are not database auth tables.

## Application audit table

`audit_events` is defined in `src/server/db/schema.ts` and was applied to the Neon production branch on 13 Nov 2026 (see `proposals-schema.md`).

| Column        | Type           | Purpose                                                                               |
| ------------- | -------------- | ------------------------------------------------------------------------------------- |
| id            | uuid           | Primary key, generated by Postgres                                                    |
| actor_user_id | text, nullable | Opaque Neon user ID from the verified server session; null for unauthenticated events |
| action        | text           | Required, nonblank event name                                                         |
| entity_type   | text           | Required, nonblank affected resource type                                             |
| entity_id     | uuid, nullable | Application resource ID                                                               |
| metadata      | jsonb          | Required object, default {}; allowlisted event details                                |
| occurred_at   | timestamptz    | Required server-generated timestamp                                                   |

Actor IDs deliberately have no foreign key into provider-managed identity tables. Audit history must survive identity deletion, and the application must not manage Neon's internal schema. Always derive the actor from a verified server session, never client-supplied identity.

Indexes cover chronological history, a resource's history, and an actor's history. Check constraints enforce nonblank action/resource type and JSON-object metadata.

Audit persistence is implemented in `src/features/audit/service.ts`: each event is written in the same SQL statement as the change it records. Still to do: restrict UPDATE/DELETE for the application's database role when provisioning permissions. Never record credentials or session tokens. Retention remains to be agreed; no automatic deletion is configured.

## Migration state

`drizzle/0000_audit_events.sql` and `drizzle/0001_proposals.sql` were applied to the Neon production branch on 13 Nov 2026 and are recorded in `drizzle.__drizzle_migrations`.

The note that the old local users/sessions migration was never applied turned out to be wrong. Production still has its tables (`user`, `account`, `session`, `verification`, `allowed_email`, `audit_event`, `rate_limit`) and its row in `drizzle.__drizzle_migrations`. They're unused and nearly empty, and they were left in place pending a decision.
